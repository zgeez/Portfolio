L0 / Product

A compass that points instead of mapping

A direction you can read at a glance, from a device that keeps working if the phone goes away.

Turn-by-turn navigation assumes roads and a screen you are willing to stare at. For a short walk to a pinned spot (a meeting point, a campsite, a parked car) all you need is the direction and whether you are getting closer.

One red pixel marks the way the device is facing, and a cyan pointer marks the way to the destination. Line the two up and walk. A Flutter companion app sends destinations over Bluetooth Low Energy and shows live telemetry, but once a destination is stored the device navigates on its own.

L1 / System

Sensors, MCU, ring and phone

The main loop polls GPS, IMU and BLE without blocking, solves navigation, renders the ring and, once a second, publishes telemetry. Each module owns one peripheral and exposes a few plain functions, so the same navigation and ring code builds against real or simulated sensors.

L2 / Firmware

A ring that never shows a direction it cannot justify

The ring is the whole interface, so every state had to be readable without a legend after one walk. The firmware renders a strict priority order, and the device never shows a direction it cannot justify.

Render priority · highest first

Honest about uncertainty

A compass that points confidently in the wrong direction is worse than no compass. A fix is flagged as poor when HDOP exceeds 6, fewer than 4 satellites are used, or the fix is older than 2 s, and the heading is flagged when the BNO08x’s own accuracy estimate exceeds 0.35 rad (about 20°). Either condition turns the target pixel red and makes the forward pixel blink faster.

Heading failover

  • IMU heading preferred whenever valid
  • GPS course-over-ground once moving
  • Amber “need heading” state when neither exists
  • Heading expires after 500 ms without IMU data

IMU self-recovery

  • Probes both addresses, 0x4B then 0x4A
  • Re-enables reports after a sensor reset
  • Reinitializes after 1.5 s of stalled heading
  • 2 s retry backoff: a missing IMU never stalls the loop

Survives a reboot

  • Destination in the dest NVS namespace
  • Mounting offset in the imu namespace
  • Restored at boot, before BLE advertising starts
  • Power-cycle mid-walk and navigation resumes

L3 / Sensor / nav

From quaternion to pixel

The BNO08x runs its own sensor fusion and reports an AR/VR-stabilized rotation vector: a quaternion with an accuracy estimate. The firmware extracts yaw, converts it from the sensor’s counter-clockwise-from-east convention to a compass heading clockwise from north, and applies a mounting offset so pixel 0 matches the physical front of the enclosure.

// imu_module.cpp: quaternion → yaw → compass heading
yaw     = atan2(2(qw·qz + qx·qy), 1 − 2(qy² + qz²))
heading = normalize(90° − yaw + mountOffset)

// navigation → ring
delta   = wrap(bearing − heading)     // shortest turn, −180°..180°
pixel   = round(delta / 22.5°) mod 16 // relative to the forward pixel

Seeded with the session in the write-up: heading 158°, bearing 214.9° places the target three pixels clockwise. Taking the shortest signed turn before quantizing keeps the pointer from jumping across the ring when heading crosses north.

The companion app’s ring mirror re-implements the firmware’s rendering rules and was checked against them in unit tests, so the phone and the ring agree, and so does the demo above.

Bearing and distance to the destination are the great-circle initial course and distance from the current fix, computed with TinyGPS++. Arrival is declared inside a 2 m radius.

L4 / Protocol

BLE commands, telemetry and testing

The device advertises as XIAO-GPS and exposes the Nordic UART Service over NimBLE: one write characteristic for commands, one notify characteristic for replies and telemetry. Using NUS means any generic BLE terminal can drive the device. Commands are short text lines, validated on the device, and every reply is mirrored to USB serial for debugging.

CommandEffectReply
SET <lat> <lon>Store a destination; rejects out-of-range coordinatesOK SET lat=… lon=…
GETReport the stored destinationSTORED … / NO_STORED_DEST
CLRClear the destinationOK CLEARED
BRIGHT <n>Ring brightness, clamped to 4–255LED_BRIGHT n
ALIGN AUTO | RESET | ? | <deg>Zero, restore, query or set the IMU mounting offsetIMU_ALIGN offset=…

Two details that make the link dependable

A reply produced before the phone subscribes is held and flushed on subscription rather than lost, and a full status snapshot is sent the moment a client becomes ready, so a freshly connected app is never blank. On disconnect the device clears pending state and restarts advertising.

Companion app

The Flutter app scans for NUS, connects, negotiates a larger MTU and subscribes to telemetry. A live ring mirror re-implements the firmware’s rendering rules, so the phone shows what the ring shows.

Debugging

Bugs the tests caught

The destination that moved the device

  1. SymptomAfter sending a destination, the device’s location on the map briefly jumped to the destination itself.
  2. Root causeThe destination echo OK SET lat=… lon=… matched the app’s position pattern.
  3. Caught byApp unit tests that feed real firmware lines through the parser. The same harness renders the app screenshots on this page.

The pointer that jumps at north

  1. RiskQuantizing bearing − heading directly makes the pointer leap across the ring as heading crosses 0°/360°.
  2. FixTake the shortest signed turn, −180° to 180°, before quantizing to 22.5° pixels.
  3. ResultNo jump at north. Drag the heading through 0° in the Sensor / nav layer to see it.

Built with

Stack

PlatformIO on the Arduino-ESP32 framework using NimBLE-Arduino, TinyGPS++, Adafruit BNO08x and Adafruit NeoPixel, with a Flutter companion app using flutter_reactive_ble and Google Maps. Demonstrates sensor fusion, BLE GATT protocol design, state-driven embedded UI, non-volatile configuration, and cross-platform mobile integration.
