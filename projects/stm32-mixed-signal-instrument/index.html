Overview

Generate, capture and correlate from one board

The project asked whether one board a student already owns can do the work of three bench instruments, driven by an application on the host. The answer required the whole chain: firmware in C on FreeRTOS, a versioned binary protocol over USB CDC, and a PySide6 desktop application that configures the outputs, pulls captures, measures them, and decodes serial traffic.

The part that took the most work does not appear in the feature list: showing that the instrument does what it says, with measurements, tests, and stated limits.

L0 / Product

What it is and what it measures

One board, three instruments, one timeline.

A student who wants to see a signal usually needs three separate instruments, and the bench that has all three is the one they cannot take home. One board provides a 2-channel arbitrary waveform generator, a 2-channel oscilloscope, an 8-channel logic analyzer, and a combined mode that puts analog and digital capture on a single shared timeline.

A PySide6 desktop application drives it, and ships as a single Windows executable that flashes the board’s firmware itself.

  • 2–256 entry arbitrary tables

SCOPE

Oscilloscope

  • 2 inputs on PC4 and PC5
  • 1 MS/s on two channels
  • 64 to 2048 simultaneous sample pairs
  • Free-run, rising and falling triggers
  • Adjustable pre-trigger position

LOGIC

Logic Analyzer

  • 8 inputs on PE7 to PE14
  • 9.882 MS/s, sampled together
  • 64 to 4096 samples
  • Edge and masked-pattern triggers
  • UART, SPI and I2C decoding

Scope of use

This is an unprotected low-voltage prototype, not a product. Inputs must stay within the board’s own supply and reference limits: no mains, negative-voltage, or automotive inputs.

L2 / Firmware

Tasks, DMA and the protocol path

Bare-metal C with FreeRTOS. Waveform refill, acquisition, USB control and status are separated into their own tasks, coordinating four concurrent DMA streams across the DAC, dual ADC and GPIO sampling.

Four tasks, four responsibilities

Architecture view · not a measured RTOS trace
T0Waveform refill
fed by DAC circular DMA
  • Keeps the DAC’s circular DMA buffer fed, half by half
  • 1.28 ms refill deadline
  • A missed half faults and stops the timer rather than repeating stale samples
T1Acquisition
fed by ADC or GPIO DMA
  • Scope (dual ADC + DMA) or logic (GPIO + DMA), never both at once

T2USB control
fed by CDC callbacks → notify
  • Services the host’s binary protocol over USB CDC
  • Woken by task notification from the CDC RX/TX-complete callbacks
  • Otherwise runs on a 10 ms idle timeout
T3Status
fed by —
  • Runs in its own task, separate from the data paths

Debug log · postmortem

Finding a 20 ms latency floor

  1. SymptomEvery request to the device took almost exactly 20 ms.
  2. ObservationA capture transfer was always an exact multiple of that figure.
  3. HypothesisA genuine throughput limit does not quantize that cleanly, but a timeout does: look at the scheduling path, not bandwidth.
  4. Root causetasks_notify_control() was defined and declared but never called from the CDC callbacks, so the control task ran only on its 10 ms idle timeout and reception was not rearmed until it did. The transmit-complete callback had the same gap.
  5. FixNotify the control task from both the RX and TX-complete callbacks, inside the CubeMX user-code regions so the fix survives regeneration.
  6. Result19.997 ms → 0.221 ms median command round trip; 2.40 → 206 kB/s capture throughput.

L3 / Hardware

Timers, converters and pins

The distinctive part of the instrument is not the instrument count; it is that two capture paths running at different rates can be compared against each other. Every timer on the device divides the same crystal, which is what makes a shared timebase possible in the first place.

TIM1’s trigger output releases a slaved TIM2, so a logic capture and an analog capture start from one hardware event rather than from two software commands that happen to be close together.

L4 / Signals

One capture, one timeline

Each stream reports where its own window begins relative to the shared start, and the application draws both against one axis with zero at the trigger. Only one stream holds the trigger; the other free-runs and is placed by index. Where the two windows do not overlap, the display says so.

A shared start is not a shared sampling instant

Measured skew between the two paths is −120 ns. That figure is not noise and it is not a defect: it matches the ADC’s 143 ns sample-and-hold aperture, so the number was traced to a specific mechanism rather than left as a residual.

No jitter is resolvable above the sampling quantization. The skew is measured against the device’s own reference output, which shares the sampler’s clock, so it bounds the two acquisition paths against each other rather than against an independent time base.

Testing & evidence

Validation

Rather than assume the DMA paths keep up, sample loss was bounded below 1 in 81,000 samples with no isolated drops, measured against an on-board timer reference across the worst of four rates, 30 captures each.

The C suites compile the actual firmware sources rather than a reimplementation, so a host test failing means the firmware is wrong and not that a stand-in drifted from it.

Limitations

Stated limits

The characterization document lists what is not established as carefully as what is. These are the limits as written, not caveats added afterwards.

AreaWhat is not establishedWhy
Analog accuracyAbsolute amplitude accuracy, distortion and bandwidth are uncharacterized.Loopback alone cannot isolate which path contributes an error, and PA4 is loaded by the board’s audio codec connection.
Time-base accuracyIndependent time-base accuracy is unmeasured.Every rate divides one crystal, so a frequency error is invisible from inside the device.
Short pulsesAsynchronous pulse limits are uncharacterized; a short pulse can be missed without a DMA error.GPIO reads land when DMA wins the bus rather than exactly at the timer edge. The 10 MS/s setting is experimental.
Protocol decodingDecoder checks used generated patterns, not independent external devices.UART, SPI and I2C decoding was exercised against the instrument’s own outputs.
Skew referenceSkew bounds the two acquisition paths against each other, not against an independent time base.It is measured against the device’s own reference output, which shares the sampler’s clock.
